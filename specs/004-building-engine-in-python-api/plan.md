# Plan 004 — Building engine in the Python API

**Spec:** [spec.md](./spec.md) · **Status:** Draft (waiting for the spec to be approved and §8 questions 1–2 answered)

## 1. Summary
Move the question tree and engineering constants into a shared JSON file (`shared/building/*.json`) that both JS and Python load. Port the formula code (`cutting`, `welding`, `takeoff`) to `engine/ultimatum/domains/building/`. Prove the two are identical with a generated case file (`building_cases.json`, produced by JS and asserted by pytest). Expose four endpoint groups.

## 3. Architecture & files
```
shared/building/questions.json      ← question tree as data (show/def rules as small expressions)
shared/building/constants.json      ← sections, process table, rebar ratios, presets, default rates
engine/ultimatum/domains/building/
    questions.py   sections.py   cutting.py   welding.py   takeoff.py
engine/ultimatum/api.py             ← /v1/building/* routes
web/src/domains/building/*.js       ← read shared JSON instead of hard-coded tables
web/tests/fixtures/building_cases.json   ← generated by `npm run gen:cases`
```
`show`/`def` rules in JSON use a tiny safe expression set (`eq`, `in`, `gt`, `pick_by_class`, `ceil_div`) evaluated identically in JS and Python. No `eval`.

## 5. Test strategy
- pytest `test_building_parity.py` (FR-004-02) over all cases × all key outputs.
- pytest unit tests mirroring `web/tests/building.test.js` (FR-004-01, 07).
- API tests with TestClient (FR-004-03…06).
- vitest keeps passing after JS reads the shared JSON (regression on spec 003).

## 6. Risks & mitigations
| Risk | Mitigation |
|---|---|
| Floating-point drift between JS and Python | compare with relative tolerance; same evaluation order in both |
| JSON rule language grows into a programming language | keep it to 5 operators; anything complex stays in code |
| FFD tie-breaking differs (sort stability) | stable sort on (length desc, original index) in both |
